# Day 21-22: Error Handling 심화

## 핵심 철학: Python vs Rust

|          | Python            | Rust                   |
| -------- | ----------------- | ---------------------- |
| 에러 처리 방식 | `try/except` (예외) | `Result<T, E>` (반환 타입) |
| 처리 안 하면? | 런타임에 터짐           | **컴파일 자체가 안 됨**        |
| 책임 소재    | 프로그래머의 성실함        | 컴파일러가 강제               |

Rust의 핵심 원칙: **예상 가능한 실패는 컴파일 타임에 강제 처리**

---

## 에러의 두 종류

| 종류 | Rust | 용도 |
|------|------|------|
| 복구 가능 | `Result<T, E>` | 파일 없음, 파싱 실패, 네트워크 오류 등 |
| 복구 불가 | `panic!` | 프로그래머 실수, 논리적 모순 (버그) |

---

## Result<T, E> 구조

```rust
enum Result<T, E> {
    Ok(T),    // 성공 + 값
    Err(E),   // 실패 + 이유
}
```

`Option<T>`과 비교:
- `Option<T>` → 값이 있거나 없거나 (이유 없음)
- `Result<T, E>` → 성공이거나 **왜** 실패했는지까지 담음

## Result 처리 방법 4가지

```rust
use std::fs;

// 1. match — 가장 명시적, 프로덕션 코드 권장
match fs::read_to_string("file.txt") {
    Ok(content) => println!("{}", content),
    Err(e)      => println!("에러: {}", e),
}

// 2. unwrap — Err이면 panic. 프로토타입/테스트에만 사용
let content = fs::read_to_string("file.txt").unwrap();

// 3. expect — unwrap + 커스텀 에러 메시지
let content = fs::read_to_string("file.txt")
    .expect("파일을 읽을 수 없습니다");

// 4. unwrap_or_else — 에러 시 대체값 제공
let content = fs::read_to_string("file.txt")
    .unwrap_or_else(|_| String::from("기본값"));
```

## ? 연산자

에러 전파를 간결하게 — `match` 없이도 에러를 위로 전달

```rust
// ? 없이
fn read_number(path: &str) -> Result<i32, std::io::Error> {
    let text = match std::fs::read_to_string(path) {
        Ok(t)  => t,
        Err(e) => return Err(e),  // 즉시 반환
    };
    // ...
}

// ? 사용
fn read_number(path: &str) -> Result<i32, std::io::Error> {
    let text = std::fs::read_to_string(path)?;  // Err이면 즉시 반환
    let number = text.trim().parse::<i32>()?;
    Ok(number)
}
```

**? 동작 원칙:**
- `Ok(값)` → 값을 꺼내서 계속 진행
- `Err(e)` → 즉시 `return Err(e)`

**제약:** `Result`를 반환하는 함수에서만 사용 가능

## 커스텀 에러 enum

여러 에러 타입이 섞일 때 하나의 enum으로 통합:

```rust
use std::num::ParseIntError;

enum MyError {
    Io(std::io::Error),       // 파일 관련 에러
    Parse(ParseIntError),     // 숫자 변환 에러
}
```

에러 타입을 `String`으로 쓰지 않는 이유:
- 오타 가능성
- 컴파일러의 exhaustiveness check 불가
- `enum`으로 정의하면 모든 케이스 처리를 컴파일러가 강제

## From trait: 자동 에러 변환

`?`가 에러 타입을 자동 변환하는 메커니즘.
`std::io::Error` → `MyError` 변환을 Rust에게 "가르치는" 것:

```rust
impl From<std::io::Error> for MyError {
    fn from(e: std::io::Error) -> MyError {
        MyError::Io(e)
    }
}

impl From<ParseIntError> for MyError {
    fn from(e: ParseIntError) -> MyError {
        MyError::Parse(e)
    }
}
```

`From`이 구현되면 `?`가 자동으로 변환해줌:

```rust
fn read_number(path: &str) -> Result<i32, MyError> {
    let text = std::fs::read_to_string(path)?;  // io::Error → MyError 자동 변환
    let number = text.trim().parse::<i32>()?;   // ParseIntError → MyError 자동 변환
    Ok(number)
}
```

## panic! vs Result 선택 기준

| 상황 | 선택 | 이유 |
|------|------|------|
| 파일이 없을 수 있음 | `Result` | 예상 가능한 실패 |
| 네트워크 오류 | `Result` | 예상 가능한 실패 |
| 배열 범위 초과 (버그) | `panic!` | 프로그래머 실수 |
| 불변식이 깨짐 | `panic!` | 논리적 모순 |
| 프로토타입/테스트 | `unwrap` | 빠른 개발, 이후 교체 |

## Python 대응 요약

```python
# Python
try:
    f = open("file.txt")
    content = f.read()
except FileNotFoundError as e:
    print(f"에러: {e}")
```

```rust
// Rust
match std::fs::read_to_string("file.txt") {
    Ok(content) => println!("{}", content),
    Err(e)      => println!("에러: {}", e),
}

// 또는 ? 사용 (함수 안에서)
let content = std::fs::read_to_string("file.txt")?;
```

**핵심 차이:** Python은 처리를 깜빡해도 컴파일 통과 → Rust는 컴파일 자체가 안 됨
